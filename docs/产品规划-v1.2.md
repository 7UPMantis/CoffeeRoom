# 咖屋 CoffeeRoom · 产品规划 v1.2

> 起因：v1.1 上线后用户反馈「点单界面不应该出现配方以及余豆，豆仓剩余警告也不该出现在点单界面」，并指出豆应该按标签筛选、部分标签应做成可选项。
> 本文档记录重构决策、数据模型、以及头脑风暴出的后续方向。
> 承接文档：[优化路线图.md](./优化路线图.md)（v1.1）、[环境搭建指南.md](./环境搭建指南.md)

---

## 一、问题诊断

v1.1 犯的错误是**把三种视角塞进了一页**：

| 视角 | 谁在看 | 该在哪 |
|---|---|---|
| 顾客 | 家人（爸爸/妈妈/自己） | 点单页 |
| 咖啡师 | 做咖啡的人 | 配方页 |
| 库存 | 管豆仓的人 | 咖啡豆页 |

v1.1 的点单页实际混入了：余豆可做 N 杯（库存）、低库存预警条（库存）、冲煮入口（咖啡师）、粉水比/水温/研磨度（咖啡师）。结果是**顾客打开点单页看到一堆数字，反而不知道该点什么**。

这不是"多加了几行"，是**信息架构错误**。同一个页面服务两种人，两边都做不好。

---

## 二、重构原则：一页一个视角

```
点单（顾客说要什么）→ 待做队列（咖啡师认领）→ 冲煮计时（按配方执行）→ 记录（含扣豆）
```

| 页面 | 只放 | 明确不放 |
|---|---|---|
| **点单** | 饮品名、分类、标签、杯数、给谁做、备注、**选豆** | 余量数字、库存警告、冲煮入口、粉水比/水温/研磨度 |
| **配方** | 待做队列、粉水比、水温、研磨、器具、时长、分步做法、冲煮入口 | 库存数字（除"可做几杯"这类警示） |
| **咖啡豆** | 余量、养豆期、用途标签、**该处理了（低余量/临期/未标用途）** | — |
| **记录** | 杯数统计、看板、筛选、每款实际用豆 | — |

**新增的「待做队列」是这个结构的胶水**。冲煮入口从点单页移走后，如果没有队列，点单和制作之间就断了；有了队列，咖啡师在配方页看到"待做 2 杯"，点开直接进计时器，做完可以标记完成。

## 三、数据模型变更

### 咖啡豆新增 `usageTags`（用途标签，多选）

```
意式 / 手冲 / 冷萃 / 通用
```

这是解决"手冲豆出现在奶咖里"的关键——原来豆和配方之间只有一根裸的 `beanId` 指针，**没有任何类型约束**，所以手冲豆当然会出现在奶咖的可选列表里。

### 配方新增 `beanType`（所需豆用途）

```
意式豆 / 手冲豆 / 冷萃豆 / 不限
```

留空则**自动推导**（优先看器具，再看分类）：

| 器具 | 推导结果 |
|---|---|
| 意式咖啡机 / 胶囊机 / 摩卡壶 | 意式豆 |
| 手冲壶 / 虹吸壶 / 法压壶 / 爱乐压 | 手冲豆 |
| 冷萃瓶 | 冷萃豆 |

| 分类（器具判断不出来时） | 推导结果 |
|---|---|
| 浓缩 / 奶咖 | 意式豆 |
| 手冲 | 手冲豆 |
| 冷饮 | 冷萃豆 |
| 特调 / 其他 | 不限 |

### 匹配兼容表

配方需要 X 时，哪些标签的豆能被选出来：

| 配方需要 | 可选豆标签 |
|---|---|
| 意式豆 | 意式、通用 |
| 手冲豆 | 手冲、通用 |
| 冷萃豆 | 冷萃、**手冲**、通用（冷萃本来就用浅中烘的手冲豆） |
| 不限 | 全部 |

**未标注用途的豆**：仍然会列出（否则历史数据全部消失），但排最后并标注「未标注用途」，保存豆子时会提醒补标。

**排序规则**：专用豆（用途精确命中）→ 通用豆 → 未标注；同组内余量多的在前。

### 订单结构变更

```js
items: [{
  recipeId, name, count,
  beanId,      // 下单时选定的豆（新增）
  beanName,    // 新增
  dose         // 新增（扣豆依据）
}]
beanUsage: [{ beanId, beanName, grams }]   // 不变，仍用于删单回补
```

历史订单缺少 `beanId`/`dose` 时，`planUsage` 会回退到配方上的默认值，保证兼容。

## 四、标签枚举化清单

自由输入是数据不一致的根源（"埃塞" / "埃塞俄比亚" / "Ethiopia" 会变成三个产地）。

| 字段 | 改前 | 改后 |
|---|---|---|
| 咖啡豆·用途 | **不存在** | ✅ 新增：意式 / 手冲 / 冷萃 / 通用（多选） |
| 咖啡豆·风味 | 自由输入 | ✅ 风味轮预置 21 项点选 + 自定义 |
| 咖啡豆·产地 | 自由输入 | ✅ 预置 15 个产地 + 自定义 |
| 咖啡豆·处理法 / 烘焙度 | 已是选项 | 保持不变 |
| 配方·标签 | 自由输入 | ✅ 预置 14 项点选 + 自定义 |
| 配方·时长 | 自由输入 | ✅ 预置 8 个常用值 + 自定义 |
| 配方·所需豆用途 | **不存在** | ✅ 新增：4 选项（含"自动"） |
| 配方·器具 / 研磨度 / 分类 | 已是选项 | 保持不变 |
| 配方·牛奶量 | 所有分类都显示 | ✅ 改为按分类条件显示 |

**为什么时长也要枚举化**：冲煮计时器要解析 `time` 字段。自由输入 "25-28s" 能解析，"大概半分钟" 就不能。格式干净是计时器可用的前提。

## 五、头脑风暴：还值得做什么

以下是我过完整个产品后想出来的方向，按「值不值得做」排序，并说明**不建议做的原因**。

### 值得做（已排入路线图）

| 想法 | 价值 | 判断 |
|---|---|---|
| **待做队列** | 补齐点单→制作的断点 | ✅ 本轮已做 |
| **豆仓「该处理了」** | 把散落的库存警告归口到一页 | ✅ 本轮已做 |
| **杯型（大杯/小杯）** | 同款饮品剂量倍数变化，比新建配方省事 | 值得做，改动小 |
| **冲煮日志回写** | 记录实际水温/粉量/时长，形成"这次比上次调了什么" | 值得做，是产品真正的差异化 |
| **补货清单分享** | 低余量豆生成"该买什么"清单，可直接发给采购的人 | 值得做，复用现有分享能力 |
| **配方复制** | 家人调出好配方后，一键复制成自己的版本 | 值得做，替代方案是让人手抄 |

### 不建议做（附理由）

| 想法 | 为什么不建议 |
|---|---|
| 会员 / 积分 / 排行榜 | 定位是家人私用。社交属性会和"给家人用"冲突，还要引入账号体系 |
| 咖啡因摄入预算 | 听起来有趣，但要医学依据和用户体重等隐私数据，投入产出比极低 |
| 咖啡豆购买/电商跳转 | 需要资质与供应链，远超当前阶段 |
| 出杯排队时间预估 | 家里做咖啡不需要排队系统，这是咖啡店的问题 |
| 自定义主题换肤 | 现有咖啡色系已足够，纯消耗工期 |
| 拍照记录成品 | 咖啡是即时消费品，拍完不会回看；封面图已经覆盖了"好看"的需求 |

**判断依据**：这个产品的用户是**一家人**，规模在 2–6 人，使用频次是每天 1–5 杯。任何需要"网络效应"或"用户量"才成立的功能都不值得做。

## 六、本轮交付（v1.2）

**数据层**
- `utils/constants.js` — 新增 `USAGE_TAGS` / `BEAN_TYPES` / `USAGE_COMPAT` / `PRESET_FLAVORS` / `PRESET_ORIGINS` / `PRESET_RECIPE_TAGS` / `PRESET_TIMES` / `LOW_STOCK_RATIO`，以及 `inferBeanType` / `beanMatchesType`
- `utils/stock.js` — 新增 `beansFor`（按用途筛豆）；`planUsage` 支持按下单选定的豆扣减
- `utils/seed.js` — 示例数据补 `usageTags`，新增第 3 支通用豆与冷萃配方

**页面**
- `pages/order/*` — 点单页去库存化：删掉余豆/警告/冲煮入口/配方参数；下单弹层新增选豆（按用途筛选）
- `pages/recipe/*` — 新增待做队列（认领 + 冲煮 + 整单完成）；配方卡显示所需豆类型
- `pages/brew/*` — 承接待做上下文（给谁做/几杯/用哪支豆）；完成后可标记该单已完成
- `pages/bean/*` — 新增「该处理了」清单（低余量/临期/未标用途）；显示用途标签
- `pages/bean-edit/*` — 用途标签多选、风味与产地改预置点选、保存时提醒补标用途
- `pages/recipe-edit/*` — 标签与时长改预置点选、新增所需豆用途、牛奶量按分类显示、默认豆按用途过滤
- `pages/record/*` — 记录里显示每款实际用豆

**验证**
- `scripts/test-logic.js` — 41 项业务逻辑测试（选豆匹配 / 扣豆回补 / 缺口判定 / 时长解析）
- `npm run verify` = 自检 + 逻辑测试

## 八、非目标（本次不做）

| 不做 | 原因 | 重启条件 |
|---|---|---|
| 把「菜单」和「配方」拆成两张表 | 一份数据两个视角已足够表达；拆表需重做全部页面，收益不成比例 | 出现"一个饮品挂多版配方且要分别统计"的真实需求 |
| 让咖啡师在冲煮时改豆 | 已选定"下单人选豆"模型；两处都能改会让扣豆口径混乱 | 出现"下单人不懂豆、每次都留空"的普遍情况 |
| 社交/会员/积分 | 与"家人私用"定位冲突 | 出现跨家庭分享的明确诉求 |
| 埋点 SDK | 家庭规模下数据量不足以支撑决策 | 需要用量化数据做判断时 |

## 待确认清单

| # | 待确认项 | 为什么需要 |
|---|---|---|
| 1 | `[待确认：当前基线]` 周打开次数、点单频次、记录页停留时长 | 路线图目标是相对的，没基线无法判断 R1–R6 是否真的改善了体验 |
| 2 | `[待确认：当前基线]` 实际数据量（订单/配方/豆各多少条） | 决定 X2 数据层整改的紧急程度（是否接近 100 条上限） |
| 3 | 家里的实际使用者有几位、是否用同一台设备 | 决定 L3 成员管理、X4 配方复制的优先级 |
| 4 | 是否真有多豆可选（同一用途下有 2 支以上豆） | 如果每种用途只有一支豆，选豆交互的价值会下降，可以简化 |
| 5 | 「通用」标签是否会被滥用（所有豆都标通用） | 若会，需要引导或限制；否则过滤机制形同虚设 |
| 6 | 杯型（X1）的倍数是固定 1.5× 还是可自定义 | 影响数据模型要不要存倍数 |

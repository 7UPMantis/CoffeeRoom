## 一、一页结论

v1.2 的**信息架构**已经对了：点单页回归顾客视角，用途过滤生效，待做队列打通了「下单 → 制作」。真机实测确认这些不是纸面设计。

**但现在的问题从"结构"变成了"密度与重复"。** 真机截图暴露的 14 个界面问题里，9 个是同一类根因：

> **卡片承载了太多维度，而同一份信息在页面上出现了两次。**

具体表现：点单页一屏只看得到 4 款饮品；配方页一屏 2.3 张卡（配方到 10 个就要滑很久）；豆仓页同一支豆在「该处理了」和「我的咖啡豆」各出现一次。这些都不是审美问题，是**屏幕利用率**问题——家庭场景下手机是唯一入口，屏幕面积就是产能。

所以 v1.3 我建议**只做减法**：不加功能，先把三个页面的信息密度提上去。同时把「选豆」按你的实际情况降级（见第三节）。

置信度约 80%。改变结论的条件：如果你实际使用时觉得"一屏看得少"无所谓、更在意信息全，那密度改造要降低优先级。

## 三、按「2–3 支豆」调整选豆策略

你说豆通常 2–3 支，这直接影响选豆这一步的价值：

**典型分布推演**

| 豆的构成 | 每款饮品的候选豆 | 选豆交互价值 |
|---|---|---|
| 1 意式 + 1 手冲 | 各 1 支（排除通用后） | ≈ 0，纯展示 |
| 1 意式 + 1 手冲 + 1 通用 | 各 2 支 | 有，但不高 |
| 2 意式 + 1 手冲 | 奶咖 2 支 / 手冲 1 支 | 只有奶咖有意义 |

**结论：选豆的价值主体不在"选"，而在"防"。**

真正必须保留的是**用途过滤**——它保证手冲豆不会出现在奶咖的可选列表里、扣错豆。而"让人挑一支"只在同用途有 2 支以上时才产生价值。

**已落地的调整**：候选豆只有 1 支时，不渲染选择器，降级为一行只读的「用豆 哥伦比亚 慧兰」。少一次点击，也少一个不必要的决策点。

**建议进一步**：如果 3 支豆的用途两两不重叠（各占一种用途），选豆在 90% 的场景下都会退化成只读展示，那这个功能就"存在但基本不触发"——这是可接受的，因为它的护栏作用仍在。

> ✅ **用户已确认（09-16）：选豆交互暂不投入。**
> 保持现状即可——候选豆只有 1 支时降级为只读展示，这已经够了，不再为"选"这一步做任何优化。
> 但**用途过滤必须保留**：它防的是"手冲豆被扣进奶咖"这种错误扣减，属于护栏，与"选"的交互价值无关，不能一起砍掉。

## 四、UI 问题清单（真机截图为证）

## 五、UI 改造方案

### 点单页：网格 → 列表行

**核心改动**：把 2 列卡片换成单列列表行，一行放完所有信息。

```
┌─────────────────────────────────────┐
│ 经典拿铁              日常 · 奶感重   │  ← 名称 + 标签同行
│ 奶咖                        − 2 ＋   │  ← 分类 + 步进器同行
└─────────────────────────────────────┘
```

收益：一屏从 4 款提升到 7–8 款；消除 U1（不再有等高拉伸）；标签不再换行。

### 配方页：参数折成一行

**核心改动**：4 格参数区（大格）折叠为一行紧凑文本，标签行限高 1 行。

```
浓缩 Espresso  ★
意式咖啡机 · 20g → 40g · 1:2 · 93℃ · 28s
[意式豆] [哥伦比亚 慧兰] [基础] [细研磨]
                    开始冲煮  设常喝  删除
```

收益：卡片高度约降 40%，一屏从 2.3 张提升到 4 张；U5 的操作区有空间做分隔。

> ⚠️ **用户已确认（09-16）：配方数量预期 30+。**
> 这个量级下**光压缩高度不够**——即使一屏 4 张，30 个配方也要滑 8 屏。
> 所以 F2 必须配上下面的分组方案一起做，否则 30+ 时依然翻不动。

#### 补充：30+ 配方的分组与排序（因数量确认而新增）

```
★ 常喝                                   2
  经典拿铁   · 奶咖 · 18g→36g
  手冲耶加   · 手冲 · 15g→240g

▾ 奶咖                                   3
  澳白 Flat White · 18g→30g
  燕麦拿铁        · 18g→36g
  焦糖玛奇朵      · 18g→36g

▸ 手冲                                   2   ← 折叠
▸ 冷饮                                   1   ← 折叠
```

四个要点：
- **常喝组置顶**：`favorite` 的排最前且不参与折叠。家庭场景里 80% 的点单就集中在这几款，其余的平时不用看
- **同类可折叠**：非常喝的按分类分组，默认折叠，点小标题展开
- **搜索必须保留**：30+ 时搜索是最快的定位手段，输入框不能为了省空间砍掉
- **组内排序**：按最近点单频次降序（需从 `orders` 聚合一次）；取不到就退回 `updatedAt`

收益：首屏从"8 屏平的列表"变成"常喝 + 分类概览"，找配方从"滑"变成"点开分类"。

### 豆仓页：该处理了 → 顶部一行动态提示

**核心改动**：不再重复渲染豆卡片，改为顶部一条可展开的提示横幅。

```
⚠ 2 支豆需要处理：1 支快用完、2 支未标用途     展开 ›
```

展开后才显示明细。收益：消除 U8 的全量重复；豆多时页面不再翻倍。

### 记录页：筛选合并 + 图表补基线

- 成员筛选与状态筛选合并为一行「筛选」入口，选中状态用 chip 反馈
- 柱状图零值日加一条 2rpx 基线，让"0 杯"可读
- 「谁喝得最多」过滤掉「不指定」，并在下单弹层把该字段改为选填带提示

### 全局：FAB 安全区

给所有带 FAB 的页面（配方/豆仓）在列表底部预留 `140rpx` 的 padding，消除 U6/U9。

## 七、非目标（本次不做）

| 不做 | 原因 | 重启条件 |
|---|---|---|
| 改 tabBar 结构（加第五个 tab） | 4 个已满，且待做队列已在配方页承载，加 tab 会稀释每个入口 | 待做队列使用频率高到需要独立入口 |
| 引入 UI 组件库（Vant/TDesign 等） | 现有原生样式已成体系，引入会增加包体与适配风险，收益仅"少写样式" | 页面数量翻倍、样式维护成本明显上升 |
| 主题换肤 / 深色模式 | 咖啡色系已足够表达品牌，深色模式要重做全部色板 | 用户主动反馈夜间使用刺眼 |
| 骨架屏 / 微动效 | 数据量小（家庭场景），加载感知不明显，投入产出比低 | 列表出现明显白屏等待 |
| 把选豆做成独立流程 | 2–3 支豆的现实下，独立流程比内联更重，且多数场景没得选 | 豆数增长到同用途多支并存 |

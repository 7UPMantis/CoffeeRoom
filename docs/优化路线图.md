## 一、一页结论

**我建议 v1.1 只做一件事：把「点单」和「咖啡豆余量」接成一个闭环。** 这是当前唯一一个"功能已经存在、但逻辑断开"的地方，也是这个产品区别于普通记录本的核心价值。

其余按投入产出排：数据看板（让记录产生价值）→ 冲煮计时器（把"配方"从静态卡片变成可执行指令）→ 分享与筛选（家人协作）。

**我的判断依据：** 产品定位是"给家人朋友用的咖啡小程序"，四个模块里「点单」「咖啡豆」各自可用，但 README 第 102 行明确写着"点单不扣减咖啡豆余量"。也就是说，用户下单 3 杯拿铁后，豆仓余量纹丝不动——**豆量数据从第一次点单起就是错的**，而"余量/临期提醒"正是这个产品花最多代码做出的能力（`utils/util.js` 的 `getBeanStatus` / `getStock` 共 80 行）。闭环不通，这套提醒就是装饰。

置信度约 85%。改变结论的条件：如果实际用法是"只在一个人手机上记配方、从不看点单页"，那这条优先级要下调——但那样咖啡豆模块也没有存在意义了。

## 二、现状诊断（代码级证据）

| # | 问题 | 影响 | 证据 |
|---|------|------|------|
| P1 | **点单不扣减咖啡豆余量** | 豆量数据从第一次点单起失真；"低余量提醒/临期提醒"失去意义；用户得手动改余量 | `pages/order/order.js` 原 `onSubmit` 只写 `orders`，不碰 `beans`；README「已知限制」第 102 行 |
| P2 | 删除订单无回补机制 | 下单后想撤销只能手动改豆量 | 同上，`orders` 与 `beans` 之间无反向链路 |
| P3 | 配方已支持上传封面，但列表不展示 | 上传的图"存了看不见"，纯浪费一次交互 | `pages/recipe-edit/recipe-edit.js` 有 `onChooseCover`；`pages/recipe/recipe.wxml` 无 `<image>` |
| P4 | 「记录」页只有 3 个计数，数据没有产出 | 用户看不到趋势、偏好、谁喝得多；记录页价值低于其他三页 | `pages/record/record.wxml` 仅 `monthCount / totalCount / orders.length` |
| P5 | 删除咖啡豆会留下悬空引用 | 配方指向已删除的豆，豆量联动会静默失效 | `pages/bean/bean.js` 原 `onDelete` 只调 `beans.remove`；README「已知限制」第 101 行 |
| P6 | 「配方」是静态卡片，无法边做边看 | 冲煮时要点亮屏幕、反复扫卡片、自己掐表 | `pages/recipe/recipe.wxml` 无任何计时/步骤推进交互 |
| P7 | 无分享入口 | "给家人用"却没法把小程序发给家人 | 全项目无 `onShareAppMessage` / `onShareTimeline` |
| P8 | 记录页无法按人/状态筛选 | 家人共用后，记录一多就翻不动 | `pages/record/record.wxml` 无条件筛选 |
| P9 | 云模式全量取回 + 内存过滤 | 数据量上限受 `limit 100` 约束，长期会截断 | `utils/store.js` `fetchAllCloud` + `query` 注释（规避索引问题的权宜方案） |

**非问题的部分（评估后确认不动）：** `store.js` 的云/本地双模降级设计合理；`getBeanStatus` 的四段状态机与配色语义清晰；`lazyCodeLoading`、分包无关的小体量下无需优化。

## 三、优化路线图

| N2 | **删除订单回补豆量**：按订单 `beanUsage` 记录还回，以 `weight` 为上限 | 项目所有者 | 删单后豆量回到点单前数值；无补偿溢出 | 本轮 | ✅ 已交付 |
| N3 | **记录页数据看板**：近 7 日杯数、分类占比、成员排行、最常点、累计耗豆 | 项目所有者 | 看板 5 项均可由订单数据自洽推出；记录页停留时长提升 [待确认：当前基线] | 本轮 | ✅ 已交付 |
| N4 | **冲煮计时器**：从配方一键开始，倒计时 + 分步清单 + 到点震动 + 屏幕常亮 | 项目所有者 | 计时误差 ≤1s/分钟；`time` 字段解析覆盖 `2:30`/`25s`/`25-28s` 三种写法 | 本轮 | ✅ 已交付 |

## 五、非目标 / 本次不做

| 不做的事 | 原因 | 重启条件 |
|---|---|---|
| 不做会员/积分/社交 | 定位是家人私用，社交属性和"给家人用"冲突，会引入账号与审核成本 | 出现"想和非家人分享配方"的明确诉求 |
| 不做咖啡豆购买/电商跳转 | 需要资质与供应链，投入远超产品当前阶段价值 | 补货清单被高频使用且有商业化意愿 |
| 不做 iOS 虚拟支付 | 小程序虚拟支付有主体与类目门槛，本项目无变现目标 | 明确要对外收费 |
| 不做自定义主题/换肤 | 现有咖啡色系已足够，收益低 | 用户主动反馈颜色问题 |
| 不改 `store.js` 双模架构 | 现在改动会牵动全部页面，风险大于收益 | v1.2 的 X1 数据层整改时一并处理 |
| 不做埋点 SDK | 家人私用规模下，埋点数据不足以支撑决策 | 需要用户量级判断时（如 L3） |

## 六、风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| 扣豆逻辑假定「一次点单 = 消耗配方标注的豆量」 | 若实际冲煮会临时换豆，扣减会与实际不符 | 订单里保留 `beanUsage` 明细，可加"实际用豆"修正入口（归入 L1） |
| 配方 `dose` 为空或为 0 | 该配方不参与扣减，用户可能误以为会扣 | 已处理：下单弹层明确标注"未关联咖啡豆，不扣豆量"，配方页也标"未关联豆" |
| 云模式 `limit 100` 截断 | 记录超过 100 条后看板统计会偏小 | 归入 X1；短期可在记录页提示条数上限 |
| 本地模式封面是临时路径 | 重启后封面失效（原有已知限制） | 保持现状，环境指南中说明；云模式下无此问题 |
| 微信开发者工具未安装 | 无法本地编译/预览/上传云函数 | 见 `docs/环境搭建指南.md` |
